# Tyll platform demo: instructions for Claude

Tyll is a hospitality intelligence and operations platform. This repository is its interactive demo for a fictional two-hotel group. Read `HANDOVER.md` (what was built, stage by stage), `DEMO_WALKTHROUGH.md` (how it is presented) and `AGENTS.md` (Next.js 16 differs from older versions; `src/proxy.ts` replaces middleware).

## Status
Stages 1–7 are complete. Stage 7 was the final planned stage: integration, notifications, search, guided demo, reset and polish. Do not start new feature stages without the owner's approval; prefer making existing workflows reliable over adding features.

## Architecture
- Next.js 16 App Router, React 19, TypeScript, Tailwind v4, zustand, Vitest. `npm run check` runs type-check, lint, tests and build.
- **Server records** (`src/lib/server/*`, one JSON store `.data/purchasing.json` via `loadStore`/`mutateStore`): purchasing and prep, events and staff support, rooms and guest service, finance, sales, shared waste and counts, notifications. API routes in `src/app/api/*` call these functions; every route uses `guard()` and checks permissions, hotel and record ownership itself.
- **Browser-held (Stage 2):** investigation decisions, price and recipe changes and receipt corrections live in the zustand store (`src/lib/store.ts`). Waste and counts made in the browser are uploaded once to the server (`src/lib/shared-stock.ts`).
- **The dataset** (`src/lib/data/generate.ts`) is deterministic: sales, deliveries with supplier invoices, counts and the seeded investigations.
- **Notifications:** `src/lib/server/notify.ts`. Call `notify()` inside a store change when work passes to someone else, and `resolve()` when it is done. Emails are logged as previews unless a provider is configured.
- **Search:** `src/lib/server/search.ts`, built only from the same list functions the screens use, so results respect access.
- **Guided demo and reset:** `src/components/shell/demo-guide.tsx` and `src/lib/server/demo.ts`. When you add seeded data, make sure the reset scopes restore it.

## Navigation rules
- The sidebar follows the three sections of tyll.ai, set in one list, `lib/nav.ts`. At the top, one Log waste button opens the logging sheet from any screen (there is no floating button on desktop). Then Overview and Alerts, then three section titles that open and close: **Stock and waste** (Stock levels, Waste and breakage, Counts and missing stock, Over pouring), **Purchasing** (Predictions, Orders, Deliveries and invoices), **Revenue and reconciliation** (Revenue, Flagged transactions, Reports). Only one section is open at a time, the one you are in, and a closed title shows how many things wait inside. Settings and help (Settings, Other tools, Help and tour, Try a look) is one folded title at the foot. Each page appears once: similar pages are merged into one item and reached by the tabs on that page (`also` in `lib/nav.ts`; `PurchasingTabs` joins Deliveries checked, Invoice approval, Order approvals and Budgets). Never repeat a sidebar item as a link inside another page, in the profile menu or on Reports; only Overview may point to the sections. Reports lists only records with no sidebar item (recipes, item history, the Money Back List, room charges, tips, menu). Phones get a bottom bar of Overview, Stock, Log waste (opens the sheet), Predictions, Revenue and More (the same folded menu). Links do a full page load only when the public demo must change role (`demoRoleFits`), and never prefetch, because a prefetch can switch the demo role. Items marked `needs` are hidden from roles without that permission.
- Lists sort by what needs a manager first: money at stake, overdue first, open before closed; long lists group by supplier or outlet with a subtotal and one header row. Losses are amber or red, never the section colour.
- Every main page starts the same way: `PageHeader` (title, the question the page answers, and "Simulated data"), then `SummaryBar`, then the page's tabs: three or four numbers, each with a label, a value and a comparison (`versus` in `lib/domain/trends.ts`), each opening the records behind it (`href` or `onClick`), plus one `StripTrend` of the last 30 days and the one primary button. Every trend has an Open button: a large view (`TrendExplorer` in `components/charts.tsx`) where related lines (`series`) switch on and off, with points, an average line and a plain explanation of each line. Lines in different units get their own chart, never a second axis; colours follow a line's place in its own chart, with a dash pattern as a second cue. Each page offers only its 2 to 4 vital lines, and a 7 day average option takes out the daily noise. Overview is the one exception to the number strip (see below). The phone top bar is one row (role and language are in the profile menu). Comparisons say the direction in words; colour and icon only add to it. Trends use only records that exist: deliveries and supplier invoices cover 13 days, so their trends say so; stock levels have no history, so they compare with par. Then `Section` and `SectionLink` rows. One primary button per screen; secondary actions are text links (`textLink`).
- Every sub page has one exit, `BackToMain` in the sticky top bar of `app-shell.tsx`, so it never covers content, ruled by `lib/back.ts`: it returns to the main page you came from, or the page's own main page. Pages listed in a sidebar section are main pages. Never add a page's own exit to its main page. Steps inside a section (such as All items) stay on the page.
- Nothing long is visible by default. A list with its own filters and search gets a sub page (`SectionLink`). Short context gets a `Section`, which remembers open or closed per person in this browser. Every closed row says in one line what is inside. At most one chart per page by default.
- Anything shown on two pages lives on one page and is linked from the other. The order recommendation lives on Predictions. Over pouring and missing drinks live on Over pouring (`/drinks`, in Stock and waste), with sold, used and not explained always on show, and the detail in closed rows. Flagged bills live on the Flags tab of Revenue. `topAlerts` puts one alert from each area first. One job is one alert: critical items, low items and supplier invoices are each grouped, and every amount says what it is (to order, at risk, not billed). An order is never counted as money at risk. The three way check of each delivery (ordered, delivered, invoiced, with the gap in units and money) lives on Deliveries and invoices (`/stock?tab=suppliers`).
- Overview opens with two numbers only, money lost this month and money saved this month (the owner removed the rows beneath them on 17 November 2026). Clicking either opens a drawer (`LedgerBars` in `home.tsx`) that draws lost and saved as two bars on one scale for each kind of loss (waste, breakage, drinks not billed, flagged bills, supplier invoice differences, stock missing at counts), each row linked to its records. Bills and counts are split by `period`, so no money is counted twice. Saved is recovered on closed cases (records) plus, for waste, breakage and drinks, any loss below last month's daily pace (`paceSaving` in `lib/domain/trends.ts`, labelled estimate, full days only). A row above last month's pace says so and never cancels another row's saving (`lostAndSaved`). Supplier invoices count as saved only once a credit is recorded. A Morning brief button previews the 7 AM summary (nothing is sent). Deliveries with an invoice difference offer "Draft a credit request": a polite email to copy, never sent by Tyll. Order approvals and Budgets are reached from the finance page, not the Deliveries tabs. Other tools is hidden in the public demo.
- Overview (rebuilt 17 November 2026 because it showed too much at once) is three things and fits one laptop screen: on the left, money lost and saved this month over the 30 day trend of money lost per day; on the right, "Needs you today", the three `topAlerts`, numbered, which the header's "3 things need you today" promises; below, one row of four feature cards in their original style (`Card`: icon and name, one large number, one line, a small picture and one neutral button; the owner asked to keep this style on 17 November 2026): Stock levels, Drinks not billed (the largest leak), Predictions and Revenue. No fact appears twice on the page. Drawers (`Drawer` in `ui.tsx`) open to half the screen on tablets and up, full width on phones.
- Predictions shows the reasoning next to every quantity (average use, in stock, when it would arrive, days covered), lets the manager change the quantity (`usePlanEdits`, sent to `buildMonthOrder` as `quantities`), and marks a recommendation for manager review by a stated rule (`reviewReason`): more than 1.5 times the last 4 weeks of use, a fresh item covering more days than it keeps, or low forecast confidence.
- The "Start free 30 day pilot" link (`lib/pilot.ts`) appears in the top bar only after a useful moment: a built order, an opened flagged case or an invoice with a difference.
- Frontline staff use `/staff` (phone-first). `/count` is a full screen flow with no sidebar.

## Design rules
- The look comes from the brand artwork: black logo, white cards, the website's moving silver wave behind every page in light and dark (`SilverWave`, `lib/wave.ts` copied from the website; brand panels keep the still artwork in `public/brand/tyll-waves.svg`), and a glass sidebar. Primary buttons, the selected page and focus rings are the deep indigo of tyll.ai, `#3B3F9C` (the owner asked for darker, calmer colours on 16 November 2026; bright shades looked unprofessional). Light is the default; dark is an optional toggle in the profile menu.
- Each sidebar section has one colour, used for its heading, icons, charts, links and money figures: Stock and waste teal `#0F5E58`, Purchasing blue `#1F4F8F`, Revenue and reconciliation violet `#5E3A8C`; Overview and Alerts indigo. All pass WCAG AA on white and on the silver page. The page colour follows the sidebar section (`sectionOf` in `lib/nav.ts`), then `MODULE_TONE`; values in `tokens.css`. Never pick a colour by hand.
- The look is chosen (17 November 2026): section colours and medium waves. The Try a look panel is removed and old saved choices are ignored (`useLookSync`); `look-picker.tsx` is no longer used.
- All colours, type sizes, radii and shadows are tokens in `src/app/tokens.css`. Red only for real losses and critical problems, amber for what needs attention, green for resolved, always with a word or icon beside the colour. Chart colours are validated separately (`--chart-a`, `--chart-b`).
- Visual rules (17 November 2026 review): amber and red only inside status badges and warnings, never on ordinary money; figures in tables are ink, emphasised by weight. One badge style (`Badge`: a 22px tinted pill with a dot; `ink` is indigo tint, never solid). Charts: straight lines, never curves; the main line in the section colour, comparisons in grey (`--chart-b`); counts as bars; axis labels on one line. Cards never nest more than two deep: a card inside an open `Section` loses its frame. Number rows: labels may take two lines but every figure shares one line and is never cut off. Whole AED for amounts, decimals only for unit prices. Litres are written L (`unitLabel`). In dark mode the primary stays indigo (#5A5FC8, white text) and the wave stays faint.
- Motion is 150 to 200 ms and only answers a person's action. The one exception is the slow background wave, which the owner asked for; it stops with reduced motion and while the tab is hidden. No dashes as punctuation in copy.

## Stock prediction and Pour Control
- Item lists sit under hotel categories (`STOCK_GROUPS`, `groupByStock` in `lib/data/locations.ts`). Stock, Predictions and Log waste are split into Food, Beverage and Inventory (`stockAreaOf` in `lib/data/locations.ts`). Inventory is glassware, china and hotel supplies. Waste and breakage share one record system; only the views are separate. Build order still makes one draft across all three.
- `monthPlanFor` in `lib/server/purchasing.ts` is the one plan to month end. Overview, Stock and All alerts all read it through `lib/alert-feed.tsx`, so they agree. `buildMonthOrder` turns it into one draft request.
- Critical means an order placed today would arrive too late. Low means the order must go by tomorrow, or under half of par is left.
- `lib/domain/pour.ts`: glasses sold are POS lines. **Bottles opened are simulated**, because the POS does not record them, and the one house wine on the menu is shared across four labels. Say so on screen. Each pattern shows the team on that shift from till logins (`teamOn` in `lib/server/pour.ts`), possible reasons and how to help (`pourReasons`, fixed rules, labelled "To check, not proven", never AI, never naming anyone). Names appear only to managers, only after "Show who was on", with "Being on shift is not proof of who poured" (set by the owner on 16 November 2026). Waste has no time of day, so it gets reasons and help by outlet and reason, not by shift. "Who was on, day by day" (`WhoWasOn`, `staffView` in `lib/server/pour.ts`) sets each outlet's daily not billed line against the rota; a person is marked "Stands out" only when the gap between their shifts and the others is 3 or more standard errors, so random rotas never point at anyone. The rota is simulated (`lib/domain/rota.ts`, every login rings bills daily in the POS data); the one planted story is the Lobby Lounge bartender (LBY-S5), whose shifts carry the heavy pours (`PERSON` in `lib/domain/pour.ts`), and a test pins that only this person stands out. The logo is the vector from tyll.ai, copied path for path in `components/brand.tsx`. There is no Early access badge.
- Log waste (`components/shell/breakage.tsx`) covers food, drinks and inventory, and must stay two taps on its page: item, number. From anywhere it is four: open, item, reason (optional), number. The confirmation says what it cost. Count (`components/stock/count-flow.tsx`) keeps its walking order on the server (`countRoutes`) and its progress in the browser.

## Source-of-truth rules
- One record per thing: purchase requests, events, rooms, tasks and invoices are never copied. Finance figures are derived from requests, deliveries and invoices; Stage 3's budget panel reads the same function.
- Keep stages of money apart: requested, approved commitment, delivered, invoiced, recorded expense. Payments are not recorded. Pipeline, contract value and revenue are different. AED and QAR are never added together.
- Corrections never overwrite: add a correction record and keep the original.

## Product rules
- Never blame staff. Show facts and uncertainty; never label anything fraud or theft. Possible causes are hypotheses until verified.
- Label estimates and simulated data. Nothing here is AI or a live integration. Never claim an email, booking or confirmation happened unless it did.
- Hiding a button is not security: check on the server.

## Seeded demo cases
The public demo sends a shorter list of flags (`lib/data/demo-cases.ts`, applied in `lib/server/snapshot.ts`): the worked examples, the largest open case at each outlet and recent closed cases. Every other mode keeps the full set.
Coca-Cola at The Terrace (8 cans unexplained), house wine at Lobby Lounge (750 ml; 250 ml at 175 ml), wagyu beef (1.8 kg), the hero order TRC-1013-198, VIP suite 1211 predicted late, EVT-DXB-0001 short of staff, invoice MEAT-1011 (chicken invoiced beyond delivery). Tests in `src/lib/__tests__` pin these numbers; keep them passing.

## Languages
English, German, Italian and Arabic, chosen in the top bar (`components/shell/language.tsx`). Screens stay written in English: `lib/i18n/dom.ts` translates text as it renders and `lib/i18n/translate.ts` looks it up in `lib/i18n/messages.json`. Figures, dates, codes and names are lifted out first, so `{0} items` covers every count. Text with no entry shows in English; `window.__tyllMissing` lists it. Add entries with `python3 scripts/i18n-add.py lines.txt` (one line per text: English | Deutsch | Italiano | العربية, `{}` for each figure, date or name). Translated so far: the main features and Reconciliation; Events, Rooms, Flow, My tasks, the Staff app and the tours are still English. Use logical classes (`ms-`, `pe-`, `start-`, `text-end`), never `ml-`, `pr-`, `left-` or `text-right`, so Arabic mirrors.

## Brand
Inter and Noto Sans Arabic, regular weight titles with tight tracking, pill buttons, ease `cubic-bezier(.22,1,.36,1)`, white and black with silver waves, one accent per section. The logo is the supplied artwork; the wordmark shows "Tyll" (`public/brand/tyll-lockup-ink-tyll.png`). Never redraw it.

## Working rules
- Show the owner the production build (preview config `tyll-platform`, `next start`), rebuilt with `npm run check`. Live reload on the dev server (`tyll-dev`) can send open tabs into a reload loop, so use dev only while editing, with one tab open.
- Make focused changes; keep the design. Run `npm run check` and test in a browser before reporting. Do not run a build while the dev server is running without restarting the dev server after. `USER_TEST.md` is the script for testing with hotel managers. Never claim a test passed unless it ran.
- The public demo has no entry page or sign-in: any address opens directly as a role that may see it. `/welcome` only shows if the demo cannot start.
- Do not deploy publicly, connect real systems, or commit secrets. Do not ask for GitHub tokens; the owner pushes with `git push origin main`.
